## Why Each Layer Exists

### KoboldCPP (Elypha hybrid-cpp fork)

The model server — the only component that touches the GPU and runs inference. It loads the GGUF model, manages the KV cache and hybrid checkpoint slots, and exposes an OpenAI-compatible HTTP API on port 5001.

The **Elypha fork** specifically is used because upstream KoboldCPP and llama.cpp don't correctly restore recurrent state for hybrid/recurrent architectures like Qwen3.5. The fork adds `--hybridcheckpointslots` and `--hybridcheckpointinterval` flags that fix this. For standard transformer models it's identical to upstream.

KoboldCPP is not exposed to the host — only LiteLLM talks to it, over the internal Docker network.

### LiteLLM

The API proxy layer. It sits between the frontend and the model server and provides:

- **A stable API surface** — Open WebUI always talks to `litellm:4000` using the OpenAI format, regardless of what's running behind it. Swapping the model server or adding a second one doesn't require touching the frontend config.
- **OpenTelemetry tracing** — LiteLLM emits OTEL spans for every request via its `otel` callback, giving you per-request latency and token count data without instrumenting KoboldCPP directly.
- **Parameter normalisation** — the `drop_params: true` setting silently discards any parameters the model server doesn't support, preventing errors from clients that send OpenAI-specific fields.

### SearXNG

The search middleware layer. It sits between all search consumers (Open WebUI, n8n agents) and the upstream search backend, providing a single consistent JSON API endpoint on `searxng:8080`.

The primary engine is Brave's scraping engine — free, no API key, Brave's own index. A secondary `braveapi` engine is configured but token-gated: it only activates when a caller includes the `SEARXNG_BRAVEAPI_TOKEN` in the request, acting as an explicit paid fallback that agents can escalate to when the scraper fails or returns poor results.

SearXNG is not exposed to the host — it is internal middleware, not a user-facing service. The UI it ships with is inaccessible from outside the `llm-stack` network and unused by any service in the stack.

### Open WebUI

The chat interface. Connects to LiteLLM as its OpenAI backend and to SearXNG for web search. Handles conversation history, system prompts, and user sessions locally — none of that data leaves the machine.

### OpenLIT

The observability dashboard. Reads from ClickHouse and visualises inference traces (latency, token usage) and GPU metrics (utilisation, VRAM, power draw, temperature) over time. Also handles its own user authentication via NextAuth.

### OpenTelemetry Collector

The telemetry backbone. Receives signals from two sources — LiteLLM (inference traces) and the GPU collector (hardware metrics) — applies transform processors to normalise naming, batches data, and exports to ClickHouse. Nothing else in the stack writes to ClickHouse directly.

Having a collector as a dedicated intermediary means you can add new exporters (e.g. Prometheus, Jaeger) or new receivers without touching the producers.

### otel-gpu-collector

A sidecar that polls `nvidia-smi` and emits raw GPU hardware metrics as OTEL metrics to the collector. Tagged with `GPU_APPLICATION_NAME` and `GPU_ENVIRONMENT` from `.env` for dashboard filtering.

### ClickHouse

Columnar database used as the single storage backend for all telemetry. Chosen because OpenLIT is built around it and it handles the aggregation queries (averages over time windows, group-by model) efficiently. Not accessed directly during normal operation.

## Docker Compose Structure

The stack is split across multiple Compose files and assembled with `include`:

```
docker-compose.yml
├── Infrastructure/infrastructure.yml
│   ├── backend/backend.yml
│   │   └── koboldocpp_Elypha/koboldcpp.yml
│   ├── middleware/middleware.yml
│   │   ├── litellm/litellm.yml
│   │   ├── open_telemetry/open_telemetry.yml
│   │   └── searxng/searxng.yml
│   └── database/database.yml
│       └── clickhouse/clickhouse.yml
└── Frontend/frontend.yml
    ├── open_webui/open_webui.yml
    └── openlit/openlit.yml
```

Each leaf file is self-contained and can be brought up independently for development or debugging. The shared `llm-stack` Docker network (created manually before first run) is the only coupling between them.

## Network

All services communicate over a single external Docker network: `llm-stack`.

It is declared `external: true` in every Compose file, meaning it must be created before any service starts:

```bash
docker network create llm-stack
```

Only two services expose ports to the host:
- **Open WebUI** on `2601`
- **OpenLIT** on `3000`

Everything else is internal — LiteLLM, KoboldCPP, SearXNG, ClickHouse, and the OTEL collector are reachable only from within the `llm-stack` network.

SearXNG makes outbound requests to Brave Search (scraper or API) depending on the query. These are egress-only — no inbound exposure.

## Data Flow: Inference Request

```
1. User sends a message in Open WebUI
2. Open WebUI POSTs to LiteLLM at litellm:4000/v1/chat/completions
3. LiteLLM emits an OTEL span to otel-collector:4318
4. LiteLLM forwards the request to KoboldCPP at model-server:5001/v1
5. KoboldCPP runs inference on the GPU, streams tokens back
6. LiteLLM streams the response back to Open WebUI
7. OTEL span is closed with token counts and latency
8. OTEL Collector batches and writes the span to ClickHouse
9. OpenLIT reads from ClickHouse and updates the dashboard
```

## Data Flow: Web Search Request

```
1. Open WebUI triggers a web search (user toggled search, or query rewrite fired)
2. Open WebUI GETs searxng:8080/search?q=<query>&format=json
3. SearXNG queries Brave scraper → returns ranked results
4. If the agent determines results are poor:
   a. Agent retries with &tokens=<SEARXNG_BRAVEAPI_TOKEN>
   b. SearXNG activates braveapi engine → calls Brave Search API
5. Results returned to caller as JSON
6. Open WebUI injects top results into the LLM context via RAG pipeline
```

## What Happens If You Remove a Layer

| Removed service | Impact |
|---|---|
| **LiteLLM** | Open WebUI has no backend — all inference stops |
| **KoboldCPP** | LiteLLM has nothing to route to — inference stops |
| **SearXNG** | Web search stops for Open WebUI and n8n agents — inference continues |
| **OTEL Collector** | Traces and GPU metrics stop being collected — inference continues |
| **otel-gpu-collector** | GPU metrics stop — inference and traces continue |
| **ClickHouse** | Telemetry can't be stored — OpenLIT goes down, inference continues |
| **OpenLIT** | Dashboard unavailable — everything else continues |
| **Open WebUI** | No chat UI — inference still accessible via LiteLLM API directly |
