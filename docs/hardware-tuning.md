# Hardware Tuning

This doc covers the knobs that matter for running the stack on different hardware. The values in `koboldcpp.yml` are tuned for the reference machine — if your GPU, RAM, or model differs, this is where to start.

---

**Tested hardware**

| Component | Spec |
|---|---|
| CPU | AMD Ryzen 9 3900X (12c / 24t) |
| RAM | 48 GB DDR4 |
| GPU | NVIDIA RTX 3080 10 GB LHR |

**Runtime VRAM usage**

| Process | VRAM |
|---|---|
| KoboldCPP (model + KV cache) | ~8.4 GB |
| System total | ~9.0 GB |

## The Three Budgets

Everything in the config is a negotiation between three resources:

1. **VRAM** — model weights + KV cache live here. Hardest constraint on consumer GPUs.
2. **System RAM** — hybrid checkpoint slots live here. Softer constraint, but matters on 16–32 GB machines.
3. **Context window** — what the model can "see" at once. Directly drives KV cache size.

They interact: a larger context requires more VRAM for KV cache, which may force you to lower KV quantization or reduce context.

---

## VRAM: Model Weights

The model weights are the fixed cost. For GGUF quantizations of a 9B model:

| Quantization | Approx. size |
|---|---|
| Q8_0 | ~9.4 GB |
| Q5_K_S / Q5_K_M | ~6.1–6.3 GB |
| Q4_K_M | ~5.3 GB |
| Q3_K_M | ~4.5 GB |

The reference setup uses **Q5_K_S**, which leaves ~3.6 GB headroom on a 10 GB card before the KV cache is factored in.

> General rule: if your model weights alone exceed ~80% of VRAM, you're going to have a bad time at any meaningful context size.

---

## VRAM: KV Cache

The KV cache is the variable cost — it scales with context size and the `--quantkv` setting.

`--quantkv` values in KoboldCPP:

| Flag value | Format | Memory per token (relative) |
|---|---|---|
| `0` | FP16 (full precision) | 1× |
| `1` | Q8 | ~0.5× |
| `2` | Q4 | ~0.25× |

For the reference machine, **Q8 KV (`--quantkv 1`) at 128K context fits** within the ~3.6 GB headroom left after weights. If you're on a card with less headroom (e.g. 8 GB total), dropping to Q4 (`--quantkv 2`) or reducing context to 65536 is the first lever to pull.

---

## Context Size

```yaml
- --contextsize
- "131072"   # 128K — reference config
```

Practical tiers to consider:

| Context | Use case |
|---|---|
| `131072` (128K) | Long documents, large codebases, extended conversations |
| `65536` (64K) | General use, good balance on 8–10 GB cards |
| `32768` (32K) | Tight VRAM budgets or larger models |

Halving context roughly halves KV cache VRAM. If you're running out of VRAM, cutting context is the most impactful change you can make.

## GPU Layers

```yaml
- --gpulayers
- "99"   # all layers in VRAM
```

`99` is a sentinel that tells KoboldCPP to push as many layers as possible to the GPU. For a 9B model that fits entirely in VRAM, this is correct — no layers run on CPU.

If your model is **too large for VRAM**, you can offload some layers to CPU by lowering this number. Each layer moved to CPU significantly reduces token generation speed, so this is a last resort. It's better to use a smaller model or lower quantization.

## Hybrid Checkpoint Slots (RAM)

This is specific to the Elypha hybrid-cpp fork and Qwen3.5-style recurrent/hybrid models. These are not KV cache — they store the recurrent state between generation intervals.

```yaml
- --hybridcheckpointslots
- "64"        # number of concurrent slots
- --hybridcheckpointinterval
- "1024"      # tokens between checkpoints
```

Each slot is approximately 50 MB of **system RAM** (not VRAM). 64 slots ≈ 3.2 GB RAM.

Tuning guidance:

| RAM available | Recommended slots |
|---|---|
| 48 GB+ | 64 (reference) |
| 32 GB | 32 (≈1.6 GB) |
| 16 GB | 16 (≈800 MB) — watch for pressure |

`--hybridcheckpointinterval` controls how frequently the recurrent state is snapshotted. Lower values = more granular state recovery but more RAM writes. 1024 is a reasonable default.

> **Important:** if you hit swap on a low-RAM machine, checkpoint slots are the first thing to reduce. A maxed-out swap will degrade performance more than fewer slots.

## CPU Threads

The reference config omits `--threads`, relying on KoboldCPP's default. With all layers in VRAM on a 3900X, the CPU is largely idle during inference — the GPU is the bottleneck.

If you're running a hybrid CPU/GPU split (some layers on CPU), set `--threads` explicitly:
```yaml
- --threads
- "8"   # good starting point for a 12-core CPU
```

Don't set this higher than your physical core count. Hyperthreading doesn't help for inference.

## GPU Tier Quick-Reference

Starting points for common consumer cards running a 9B model at Q5_K_S:

| GPU | VRAM | Suggested `--contextsize` | Suggested `--quantkv` |
|---|---|---|---|
| RTX 3080 10 GB / 3080 Ti | 10–12 GB | 131072 | 1 (Q8) |
| RTX 4070 / 3070 Ti | 8–12 GB | 65536–131072 | 1–2 |
| RTX 4060 Ti 16 GB | 16 GB | 131072 | 0 (FP16) |
| RTX 3070 / 4060 8 GB | 8 GB | 32768–65536 | 2 (Q4) |
| RTX 3060 12 GB | 12 GB | 65536–131072 | 1 |

These are starting points — actual fit depends on your model's layer/head configuration and what else is using VRAM (desktop compositor, browser, etc.).

## Checking VRAM Usage

```bash
watch -n 2 nvidia-smi
```

Key things to watch:
- `MiB` usage in the process table — KoboldCPP should show a stable number once loaded
- If usage is near your card's total, you have little room for KV growth during long conversations
- Spikes during generation can cause OOM if you're running close to the limit
