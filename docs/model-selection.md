# Model Selection

This stack is built around the [Elypha hybrid-cpp](https://github.com/Elypha/hybrid-cpp) fork of KoboldCPP, which adds correct hybrid/recurrent checkpoint support. That fork requirement shapes which models work well here.

---

## Why This Fork

Standard KoboldCPP and llama.cpp handle transformer models fine, but **hybrid/recurrent architectures** (models that mix attention layers with recurrent state layers) have a different inference pattern — the recurrent state needs to be saved and restored correctly across generation steps. Elypha's fork fixes this for Qwen3.5-style models.

If you use a standard transformer model (Llama, Mistral, Phi, etc.), this fork works identically to upstream KoboldCPP. The checkpoint slots simply go unused.

---

## Reference Model

The reference setup uses:

https://huggingface.co/Jackrong/Qwopus3.5-9B-v3

```
Qwopus3.5-9B-v3.Q5_K_S.gguf
```

This is a **Qwen3.5 9B** derivative in GGUF format at Q5_K_S quantization. Qwen3.5 is a hybrid architecture — it's the primary reason this fork is used.

## Compatible Model Families

### ✅ Fully supported — hybrid/recurrent

These benefit directly from the hybrid-cpp fixes:

| Family | Notes |
|---|---|
| **Qwen3.5** | Reference model family. Requires hybrid-cpp for correct recurrent state handling. |

### ✅ Fully supported — standard transformer

Any GGUF model that works with upstream KoboldCPP works here. The checkpoint slots are ignored:

| Family | Notes |
|---|---|
| **Llama 3.x** | 8B fits well at Q5 on 10 GB cards |
| **Qwen 2.5** | Strong general-purpose and coding models |
| **Mistral / Devstral** | Good coding performance at smaller sizes |
| **Phi-4** | Punches above its weight at 14B |
| **Gemma 3** | 9B/12B fit well on 10–12 GB cards |

### ⚠️ Check before using

| Family | Notes |
|---|---|
| **MoE models** (Mixtral, DeepSeek-MoE, etc.) | Expert layers inflate VRAM unpredictably — measure before committing to a context size |
| **Models >13B at Q5+** | Unlikely to fit on 10 GB — check weight size first |

## Quantization Format

This stack uses **GGUF** exclusively — it's the format KoboldCPP loads natively.

Recommended quantizations for a 10 GB card running a 9B model:

| Quantization | Size | Quality tradeoff |
|---|---|---|
| `Q5_K_S` | ~6.1 GB | Good balance — reference config |
| `Q5_K_M` | ~6.3 GB | Marginally better quality, same headroom |
| `Q4_K_M` | ~5.3 GB | Frees ~1 GB — useful if you want more KV headroom |
| `Q8_0` | ~9.4 GB | Near-lossless, leaves very little room for KV cache on 10 GB |

For larger context or lower quantkv budgets, `Q4_K_M` gives you the most flexibility. For best quality within the 10 GB envelope, `Q5_K_M` is the sweet spot.

## Chat Template Requirement

KoboldCPP is configured with a **ChatML adapter**:

```yaml
- --chatcompletionsadapter
- /app/kcpp_adapters/ChatML.json
```

This means the model you use should be trained with a **ChatML prompt format**. Most modern open-weight models (Qwen, Llama 3, Phi, Mistral Instruct) use ChatML or are compatible with it. Check the model card if you're unsure.

If a model uses a different template (e.g. Alpaca, Llama 2 chat), generation quality will degrade — the model won't correctly distinguish system/user/assistant turns. Either swap the adapter or find a ChatML-compatible variant.

## Placing the Model

Drop the `.gguf` file into:

```
Infrastructure/backend/models/<your-model>.gguf
```

Then update `koboldcpp.yml`:

```yaml
- --model
- /models/<your-model>.gguf
```

The `models/` directory is excluded from git via `.gitignore` — model files won't be committed.
